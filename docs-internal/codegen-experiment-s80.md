# コード生成の精度検証: レイヤー名とコンポーネント化の有無（2026-07-28）

「レイヤー名を整えないと生成結果がどう変わるか」を実測した記録。BACKLOGの「5-2/7-1のコード生成を一度通して実態を確認する」もこれで閉じた。

## 方法

教材専用Figmaファイルに検証用ページを作り、`task-list-final` を複製して名前を自動名に戻したものを用意した。

| | 整った側（`196:121`） | 汚した側（`264:206`） |
| --- | --- | --- |
| 総ノード数 | 121 | 121 |
| 自動名のノード | 0 | 64 |
| インスタンス | 18 | 0 |
| バリアブル紐付けのあるノード | 118 | 118 |
| テキストスタイル適用済み | 57/57 | 57/57 |

テキスト57個はFigmaが中身を名前にするため、名前が壊れたのは非テキストの64個すべて。トークンとテキストスタイルは両側で完全に同一。

コンポーネント名を変えると整った側にも影響するため、汚した側はインスタンスを18個すべて切り離した。**このため変数は「レイヤー名」と「コンポーネント化の有無」の2つが混ざっている。** 名前だけを変えた3つ目の条件は未実施。

生成は、この設計について予備知識を持たないサブエージェント2体に、同じ指示文とそれぞれのURLだけを渡して並行実行した。指示は5-2の雛形に準じ、`get_design_context` の出力だけを根拠にさせた。

## 結果

### 規模はほぼ同じ

| | 整った側 | 汚した側 |
| --- | --- | --- |
| ファイル数 | 9 | 9 |
| 総行数 | 345 | 348 |
| コンポーネント数 | 9 | 9 |
| 画像URL | 3 | 3 |

分量と分割の粒度では差が出ない。汚した側も見た目の繰り返しから9個に分割できている。

### 差が出たのはコンポーネント名

| 整った側 | 汚した側 |
| --- | --- |
| `TaskCard` | `TaskCard` |
| `StatCard` | `StatCard` |
| `TaskSection` | `TaskSection` |
| `Sidebar` | `Sidebar` |
| `NavItem` | `SidebarNavItem` |
| `Chip` | `FilterChip` |
| `PriorityTag` | `PriorityBadge` |
| `Header` | `TopBar` |
| `TaskListFinal` | `TaskListScreen` |

汚した側の名前は**コードとしては妥当**で、むしろ `FilterChip`・`SidebarNavItem` のほうが説明的なほどだった。問題は品質ではなく**デザインと語彙が一致しないこと**。「PriorityTagのパディングを直して」と言われたとき、コードに `PriorityTag` はない。

汚した側の出力にはレイヤー名が1つも含まれず、ノードは `data-node-id="264:207"` のような数値だけで識別されていた。エージェントは「コンポーネント名はすべて自分の発明で、レイヤー名を反映せよという指示は満たせなかった」と報告した。

### 大きく効いたのはコンポーネント化（バリアント）

`TaskCard` のpropsに明確な差が出た。

```
整った側: priority, title, description, category, assignee, due, done
汚した側: checkboxSrc, priority, title, description, tag, assignee, due, muted
```

- 整った側は `done` / `active` / `priority` をFigmaのバリアントから受け取り、propsの名前と値がデザインと一致した
- 汚した側は完了状態を `muted`（見た目の説明）と命名し、「意図的な完了状態なのかデザインの手落ちなのか判別できない」と報告した
- 汚した側は `checkboxSrc` をpropsに出した。呼び出し側がどちらの画像を渡すかを決める形で、状態の管理がコンポーネントの外に漏れている

これはレイヤー名ではなくコンポーネント化の効果。3-2で「状態は色の上書きではなくバリアントで表現する」と教えている理由が、そのままコードの型に出た。

## 教材の記述と食い違った点

### CSS変数が残るかは指示しだい（5-2の記述が不正確）

5-2にはこうある。

> トークンを当てておいた箇所は、`var(--surface, white)` や `var(--space/16, 16px)` のように、自分が付けた名前がCSS変数として生成コードに現れます。

実測は次のとおり。

| | `var(--...)` の出現数 |
| --- | --- |
| 整った側 | 0 |
| 汚した側 | 77 |

`get_design_context` の出力は両方とも `var(--brand,#7c3aed)` の形でトークン名を含んでいた。にもかかわらず、整った側は実値（`bg-[#7c3aed]`）に展開し、汚した側はそのまま残した。**入力の差ではなく、同じ指示に対する生成のばらつき。** 指示テンプレートの「Tailwind CSSのユーティリティクラスのみ」が、`var()` を展開する方向にも読めるのが原因と考えられる。

トークン名を残したいなら明示的に頼む必要がある。

### 画面全体を1回で読ませるとバリアントの中身の差分が落ちる

`done=true` の `task-title` には打ち消し線が入っている（Figma上で `STRIKETHROUGH` を確認）。部品単位で `get_design_context` を呼ぶと出力に `line-through` が現れる。

しかし画面全体を1回で読ませた生成では、**両側とも打ち消し線が落ちた**。整った側のエージェントは「打ち消し線などの他の差分があるかは出力からは分からない」と報告している。インスタンスはpropsの形に要約され、バリアント間の見た目の差までは展開されないため。

### チェックの丸が画像URLになる（BACKLOGの懸念は的中）

`checkbox`・`avatar`・`user-icon` が `<img src="https://www.figma.com/api/mcp/asset/...">` になった。両側とも3箇所。楕円（ELLIPSE）はSVGではなく画像アセットとして書き出される。このURLは7日で失効する。

同じカード内の `assignee` は角丸フレームなので `<div>` になっている。図形の種類で扱いが変わる。

## 裏付けられた記述

3-3と5-2の「レイヤー名が生成結果に出る」は、整った側で完全に成立した。`get_design_context` の出力に `task-list-final`・`sidebar`・`NavItem`・`stat-row`・`StatCard`・`chip-active`・`section-today`・`TaskCard`・`PriorityTag`・`task-body` などが原文のまま含まれ、コンポーネント名にそのまま反映された。

## 両側で共通して落ちたもの

- テキストスタイル名（`card-title` など7種）。スタイル定義は出力に含まれるが、どの要素がどれを使うかの対応がないため、サイズとウェイトの直書きになる
- 意味づけ。チェックボックスは `<img>`、チップとナビ項目は `<div>`。`<button>`・`<input>`・`<nav>` にはならない
- 状態（ホバー・フォーカス・無効）とインタラクション
- `lineHeight: 100` の単位が不明（%かpxか出力から確定できない）
